# Godot 渐进迁移路线

## 当前架构

当前版本以 Godot 替换 React 表现层，游戏规则和房间仍在 TypeScript 端运行。两个客户端通过同一套 WebSocket JSON 协议提交 `GameAction`。房间服检查操作者的座位，由 `gameReducer` 结算，再用 `viewFor` 为各座位生成独立的 `RoomView`。Godot 根据自己的视图展示手牌和秘密选择。[协议定义](../src/net/protocol.ts) · [房间服](../server/roomStore.ts)

Godot 从两个来源取数。每次行动的 `lastEvents` 决定本次投骰、移动、伤害和旁白的播放顺序。随项目提交的 `content_catalog.json` 提供名称、描述、稀有度、关键字等公开资料。卡牌效果的执行与随机数仍由规则引擎负责。[事件播放控制器](../godot/scripts/anim/playback_controller.gd) · [内容目录导出脚本](../scripts/export-godot-catalog.ts)

## 里程碑与验收

| 里程碑 | 当前进度 | 验收方式 |
|---|---|---|
| M1 联机棋盘 | 已实现建房、加入、重连、三阶段棋盘、投骰与结束回合，支持干扰卷轴选目标和相遇意向。主场景已有无界面测试。 | 用不同身份启动两个 Godot 客户端，或各用一个 Godot 和 Web 客户端，同房核对行动交接及断线回座。双客户端实机联调待验收。 |
| M2a 事件播放 | 已接入按事件 ID 去重的队列、旁白和跳过演出。棋盘与玩家面板按事件更新位置、生命、金币和手牌。战斗骰点、攻防归属和末击生命的显示逻辑已有测试。 | 无界面测试覆盖重复广播、连续事件、跳过演出和房间切换，并检查主场景释放后的孤立节点。 |
| M2b 可操作的战斗 | 下一步接入 PvE/PvP 选牌或空过、攻防骰展示、伤害与胜负面板，以及战利品确认。 | 先完成普通怪战斗，从投骰走到领奖并交接回合。再用两个座位验证 PvP 双方独立提交，提交期间对手只能看到提交状态。 |
| M3 其余阶段 | 待补宝箱、赐福和事件确认、缴械弃牌、装备取舍、商店、赌场、首领、成长，以及交易报价、确认和 PvP 惩罚。手牌详情及移动卷轴的参数选择也在此阶段。 | 对照 `GamePhase` 逐项检查谁能操作、其他人看到什么，以及提交后能否继续对局。 |
| M4 发行 | 待验证桌面及 Web 导出、资源与音频加载，补齐设置保存、错误上报和版本握手。 | 在目标平台使用导出包，验证内容目录可读、可加入房间并可完成对局。 |

本次基线为 60 个 Vitest 文件、660 个测试，以及 231 项 Godot 无界面检查。Godot 场景测试通过模拟广播验证客户端行为。运行命令和双实例配置见[客户端 README](../godot/README.md)。

## 完整迁移的评估方案

如果目标转为 Godot 独立运行，可以先验证本地双人热座，再决定规则引擎和房间服的迁移范围。

1. 从 TypeScript 导出固定种子的动作序列，以及每步的状态、事件和座位视图。先用种子 `8` 覆盖投骰、开宝箱、确认奖励和交接。分别对齐地图生成和对局投骰的随机序列。
2. 让现有棋盘和行动面板也能接收 Godot 本地规则产生的座位视图。验收时关闭 Node 房间服，两位玩家仍能开宝箱、交接回合，换人后只看到自己可见的手牌。
3. 用种子 `1` 对照普通怪战斗的攻防顺序、血量和战后奖励。后续按效果类型移植卡牌，复用内容目录中的公共字段，并用相同动作回放核对结算结果。
4. 若发行目标也包含 Godot 房间服，再让无界面服务端复用本地规则，逐项验证座位权限、暗牌裁剪、重连和掉线处理，再切换联机流量。
